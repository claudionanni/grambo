## View System Architecture

### Two-Layer View System
Galera operates with views at different architectural layers, each with distinct purposes and formats.

#### GCOMM Layer Views (Network Level)
**Source**: Teemu Ojala (Codership)
```
view(view_id(NON_PRIM,81e3fb0a-9e9b,24))
```

**Components**:
- **Status**: `NON_PRIM` or `PRIM` - Primary configuration status
- **Node ID**: `81e3fb0a-9e9b` - Representative node identifier
- **Sequence**: `24` - EVS protocol view sequence number

**Characteristics**:
- Lower-level networking layer perspective
- EVS sequence number has limited meaning at higher layers
- Focuses on network topology and communication
- Generated by GCOMM (Group Communication) subsystem

#### WSREP Layer Views (Replication Level)
**Source**: Teemu Ojala & Alexey Yurchenko (Codership)
```
id: 670ce4a0-9538-11f0-aa1f-168ebbd1d7d1:6
```

**Components**:
- **Cluster ID**: `670ce4a0-9538-11f0-aa1f-168ebbd1d7d1` - Unique cluster identifier (UUID)
- **View Seqno**: `6` - View sequence number from replication counter

**Critical Properties** (Alexey Yurchenko):
> "View seqno comes from the same counter as the regular replication event seqno. Primary configurations are totally ordered and get the same seqno."

- **Integrated with replication stream**: View changes are part of main replication sequence
- **Totally ordered**: Primary configurations follow strict ordering
- **True seqno**: Represents actual Configuration Change (CC) event sequence number
- **GTID compatible**: Part of Global Transaction ID sequence

## Sequence Number System

### Primary Replication Counter
- **Shared counter** for both replication events and configuration changes
- **Monotonically increasing** across all cluster events
- **Globally consistent** across all nodes in primary configuration

### Configuration ID (`conf_id`)
**Source**: Alexey Yurchenko (Codership)
- **Purpose**: Counts total configuration changes
- **Scope**: Printed at GCS (Group Communication Service) level
- **Limitation**: Never associated with UUID (not a GTID seqno)
- **Usage**: Internal tracking, not part of replication sequence

## State Transfer System

### SST→IST Relationship Pattern
**Critical Discovery**: IST follows SST to apply changes accumulated in galera.cache during SST.

**Log Pattern Sequence**:
```
WSREP: Installed new state from SST: a572a681-97f2-11f0-9f63-c7c3a72b2527:N
WSREP: Cert. index preload up to N
WSREP: ####### IST applying starts with N+1
```

**Critical Sequence Number Pattern**:
- **SST restores to**: seqno **N**
- **Cert preload up to**: seqno **N** 
- **IST starts from**: seqno **N+1**

**Technical Flow**:
1. **SST Completes**: Node receives snapshot up to seqno N
2. **Certificate Index Preload**: Loads certificate index up to seqno N  
3. **IST Applies**: Incremental changes from seqno N+1 onwards (accumulated during SST)
4. **Cache Catch-up**: Processes transactions that accumulated in galera.cache during SST

**Implementation in GRAP**:
- **SST entities** track `installed_state_seqno` and `related_ist_id`
- **IST entities** track `follows_sst_id` and `applying_from_seqno`
- **Automatic linking** when IST starts with seqno = SST_seqno + 1
- **Temporal relationship** preserved for cluster analysis

### IST (Incremental State Transfer)

#### Workflow Stages
Based on log analysis and message patterns:

1. **Preparing**: IST sender preparation phase
2. **Receiver Ready**: IST receiver preparation complete
3. **Prepared**: Both sides ready for transfer
4. **Preloading**: Certificate index preload (follows SST completion)
5. **Applying**: Transaction application in progress (from SST seqno + 1)
6. **Seqno Initialized**: Sequence number tracking established
7. **Receiving**: Active data reception phase  
8. **Received**: Data reception complete
9. **Processing**: Final processing and validation

#### Key IST Messages
```
WSREP: async IST sender starting to serve tcp://IP:PORT sending SEQNO1-SEQNO2
WSREP: IST receiver addr using tcp://IP:PORT
WSREP: Prepared IST receiver for SEQNO1-SEQNO2, listening at: tcp://IP:PORT
WSREP: Cert. index preload up to SEQNO
WSREP: ####### IST applying starts with SEQNO+1
WSREP: IST sender SEQNO1 -> SEQNO2
```

### SST (State Snapshot Transfer)

#### SST Script vs Actual Backup Transfer
**Critical Distinction**: Galera always triggers SST script on restart, but actual backup transfer may be bypassed.

**SST Script Triggered**:
```
WSREP: Running: 'wsrep_sst_mariabackup --role 'joiner' --address...
```

**Actual Backup Transfer Occurs**:
```
WSREP_SST: [INFO] Proceeding with SST (20250925 17:22:21.180)
```

**Bypass Conditions**:
- **Transactions available in galera.cache**: No backup needed, jump to IST
- **Small seqno gap**: IST sufficient for catch-up
- **Recent donor state**: Donor has required transactions cached

**Implementation in GRAP**:
- **`sst_script_triggered`**: True when SST script starts
- **`backup_transfer_occurred`**: True only when "Proceeding with SST" detected
- **`sst_status`**: Differentiates "bypassed_for_ist" vs "backup_transfer_started"

#### Error Code Analysis
Common SST error patterns and meanings:

- **Error -22**: `EINVAL - Invalid argument` - Configuration issue
- **Error -3**: `No such process` - Process termination/cleanup
- **Provider failures**: Higher-level state transfer coordination issues

## Entity Relationships

### Temporal Dependencies
1. **VIEW changes** → **State transitions** → **SST/IST events**
2. **Configuration Changes** are **replication events** with dedicated seqnos
3. **State transfers** can be **triggered by** or **trigger** view changes

### SST Bypass Pattern
**Two SST Execution Paths**:

1. **Full SST**: Script triggered → Backup transfer → IST (if needed)
   ```
   SST script → "Proceeding with SST" → Backup transfer → IST application
   ```

2. **Bypassed SST**: Script triggered → Direct IST (transactions in cache)
   ```
   SST script → IST application (no backup transfer)
   ```

**Analysis Implications**:
- **Performance**: Bypassed SST = faster recovery time
- **Cache health**: Indicates galera.cache contains required transactions
- **Cluster efficiency**: Donors have recent enough state for IST-only recovery

### Node State Correlation
- **Donor nodes**: Must be in `SYNCED` state for state transfers
- **Joiner nodes**: Transition through `JOINER` → `JOINED` → `SYNCED`
- **View membership**: Determines available donors and cluster topology

## Implementation Guidelines for GRAP

### View Entity Parsing Strategy
1. **Differentiate layers**: Separate parsing for GCOMM vs WSREP views
2. **Prioritize WSREP views**: More meaningful for cluster analysis
3. **Track seqno integration**: WSREP view seqnos are part of replication stream
4. **Correlation capability**: Link views to corresponding state transitions

### State Transfer Entity Enhancement
1. **IST workflow tracking**: Implement 8-stage IST progression monitoring
2. **Error classification**: Categorize SST/IST errors by type and severity
3. **Performance metrics**: Track transfer duration and throughput
4. **Dependency mapping**: Connect transfers to triggering view changes

### Sequence Number Handling
1. **Unified tracking**: Treat configuration changes as replication events
2. **Gap detection**: Identify missing sequences in replication stream
3. **Timeline reconstruction**: Use seqnos for temporal event ordering
4. **GTID awareness**: Respect Global Transaction ID semantics
